# Database

The intended production database is Supabase PostgreSQL. Flyway versions schema changes, with vendor-specific SQL under `db/migration/postgresql` and `db/migration/h2`. Migration V1 creates `public.user_profiles`. On PostgreSQL, `user_id` references `auth.users(id)` with cascade delete, row level security is enabled, and the `anon` and `authenticated` roles have no table grants. The Java API accesses it through a server-side database connection and scopes each operation to the verified JWT subject. V1 passed against local H2, local PostgreSQL 17, and the real Supabase project `xxdvusmvvrnqicorjczo`. The Supabase profile puts Flyway history in a separate `finsight` schema, leaving Supabase's managed `public` objects alone. Hibernate uses `ddl-auto: validate` and cannot create or alter production tables.

The `local` profile uses in-memory H2 to verify API startup without a cloud account. This is not a substitute for a PostgreSQL migration or owner access test. An optional local PostgreSQL service is defined in `infrastructure/docker/compose.postgres.yaml`; set `LOCAL_POSTGRES_PASSWORD` in an untracked `.env` before starting it.

Next domain model candidates: `financial_accounts`, `categories`, `transactions`. Create tables alongside the first use case, with owner foreign keys, uniqueness rules and indexes. Amounts will use exact decimal precision; VND is the initial currency.
